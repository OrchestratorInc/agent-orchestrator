# 产品需求确认记录（问答中）

## 已确认信息

- 产品方向：多编码 Agent 编排，不是通用聊天机器人平台。
- 基座选型：Orchestrator.inc，克隆到 E:\code\agent-orchestrator 并在独立分支改造。
- 终端形态：以 Windows 本地使用为起点，桌面界面希望接近 Codex 的会话体验。
- 交互重点：查看各 Agent 的执行过程；执行期间能与指定 Agent 交互。
- 工作方式：先建立基础骨架，再逐问逐答确认需求，最后产出详细设计。
- **控制模式（Q1）：混合模式。** 主控 Agent 默认自动规划、拆分和分配任务；用户可以随时介入指定 Agent 的会话，补充指令、暂停或调整任务分配，也可以手动创建任务。具体干预语义和审批边界后续继续确认。
- **Agent 接入策略（Q2）：可插拔 Agent Adapter。** 首发必须支持 Codex CLI、Claude Code CLI、Oh My Pi、DeepSeek Harness；适配器需隔离各执行器的启动、会话、事件流、输入/Steer、取消、能力声明和结果解析差异。具体版本、命令行入口、协议能力和认证方式在技术调研阶段逐一核实。
- **执行中交互语义（Q3）：三种方式都支持。** Steer：执行器支持时向当前运行轮次补充指令；Queue：将消息排队至合适的后续轮次；Stop & Replan：停止当前执行并保留工作区成果，由主控重新规划。Adapter 必须声明实际能力，降级时应清楚提示用户，不承诺所有执行器可即时 Steer。

- **多 Agent 协作（Q4）：分级自治协作。** 子 Agent 可以直接通信、交换结果、请求协助；但创建和分配新任务、增加并发与资源预算，必须通过主控调度器统一管理。跨 Agent 消息、任务来源和授权过程需可追踪，防止重复工作和无限派发。

- **代码与交付策略（Q5）：分级权限与自动验收。** 每个写代码的 Agent 使用独立 Git Worktree；自动进行代码审查、测试和有界次数修复。通过质量门禁后允许自动提交到任务分支；合并到目标分支、向远程仓库推送及其他高风险操作必须经用户批准。验收结果、修改 Diff 与审批记录须可追踪。

- **项目范围与执行位置（Q6）：分阶段实现。** 首版支持多仓库任务与跨仓库依赖，所有 Agent 在本机 Windows 上执行；执行层预留远程 Worker 适配接口，后续再开发远程调度、认证、工作区同步和恢复能力。远程 Worker 不属于首版交付范围。
