# Docker Agent (native ACP Chat)

AO supports the user-installed standalone `docker-agent` **v1.150.0** on Unix through its native stdio ACP server. Docker Desktop is optional. Other versions are refused until qualified. Install the official binary from [Docker's release](https://github.com/docker/docker-agent/releases/tag/v1.150.0); AO offers manual installation guidance, not a remote shell installer.

Set `AO_DOCKER_AGENT_CONFIG` in AO's launch environment to an **absolute existing native YAML config path**, and configure the selected provider's credentials using Docker Agent's native setup. AO keeps authentication `unknown`: neither config presence nor ACP's `host-credentials` availability check proves remote authorization. A live provider turn is authoritative. AO does not import Codex login or rewrite native provider configuration.

Set the config path before launching AO: project environment settings cannot override reserved `AO_*` keys. New Chat task admission checks the effective launch environment and rejects a missing, relative, nonexistent, or non-file config before creating the session or workspace. The global Chat probe rejects Windows; config checks run for each new task independently of cached capabilities. Binary inventory and unknown authentication are separate from Chat availability; a detected executable alone does not establish that Docker Agent can start.

AO currently uses its existing initials avatar for Docker Agent. No Docker brand asset with verified reuse terms has been added, so this integration deliberately retains that fallback rather than asserting a license for an upstream logo.

Select Docker Agent and Chat when creating a task. The initial model choice is `default` (the root agent's native configured model). The live Chat model menu uses Docker Agent's own `model:<configured-name>` options; arbitrary provider model names and AO reasoning-effort overrides are refused. Configure those natively. Native config, tools, hooks, and project `AGENTS.md` remain intact.

AO appends private standing instructions using Docker Agent's supported `--hook-session-start` mechanism. The JSON hook result lives in a private AO data directory; its shell command contains only the quoted file path. Native hook merging retains existing hooks. Context names the actual AO worktree so tools do not default to the source repository. It is reapplied on new/load; over 32 KiB is refused rather than truncated. Native persisted history may contain prior context. This is instruction delivery, not secret storage.

Native session databases and caches live under the selected AO data directory, scoped by AO session and conversation scope. Kill/restore loads the exact native ID and replays saved history. Unknown IDs and workspace mismatches fail; AO does not silently start fresh. The existing detached ACP host supports daemon reconnection and bounded process cleanup.

Permissions preserve native tools and user rules: AO default maps to native `default`; AO auto maps to native `balanced` (classifier-safe calls may run, others ask); bypass maps to native `autonomous` (native deny rules/guards still apply). AO accept-edits is refused because native tool annotations cannot establish that policy. Approve, reject, cancel, and turn interrupt use the ordinary ACP approval channel. Explicit native allow rules can already authorize tools, as in Docker Agent itself.

AO terminal mode, TUI/Chat handoff, reviewer support, steering, fork, and rollback are not claimed. Generic ACP exposes native commands (including compaction) and negotiated image/embedded-context/input transport; those optional surfaces were not independently exercised by the text/shell qualification. Qualification used the released Linux amd64 artifact SHA-256 `791fa6bac9f829847f00ab948f838bf54d11e0830988a5e5bce88d65ea65f2d1`, native custom OpenAI-compatible Z.ai `glm-5.3-flash`, permission controls, file edits, private instruction refresh, persisted load, and executing-shell cancellation. Routine tests run only in PR CI under the authorized VPS policy; real AO proof and capture are recorded separately in the integration report.
