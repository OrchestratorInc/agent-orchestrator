# Docker Agent (native ACP Chat)

AO supports the standalone `docker-agent` **v1.150.0 or newer** (a v1.150.0 prerelease is refused) on Unix through its native stdio ACP server. Docker Desktop is optional. On macOS and Linux, Settings → Harness → Docker Agent → Install uses `brew install docker-agent`, which installs the latest release, and updates follow it; otherwise install the latest official binary from [Docker's releases](https://github.com/docker/docker-agent/releases). Versions older than v1.150.0 are refused; v1.150.0 is the release this binding was qualified against.

With a provider key in AO's environment (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or `GEMINI_API_KEY`/`GOOGLE_API_KEY`) or saved by `docker-agent setup` in `~/.config/cagent/.env` (`$XDG_CONFIG_HOME/cagent/.env`), AO generates a private per-session Docker Agent config using Docker Agent's suggested models for the available providers, with filesystem and shell tools. To use your own configuration instead, set `AO_DOCKER_AGENT_CONFIG` to an **absolute existing native YAML config path**; AO never rewrites it. Settings → Harness → Docker Agent → Account runs `docker-agent setup`, Docker Agent's native provider setup.

Authentication starts from Docker Agent's own `docker-agent doctor --json`, which reports where each provider key comes from without printing it. With `AO_DOCKER_AGENT_CONFIG`, doctor checks that file and a failing check shows `unauthorized`. Otherwise AO checks the key of the provider its default config launches with against that provider's model-list endpoint (`OPENAI_BASE_URL` when set, as Docker Agent itself uses), which authenticates without running or billing a model turn: accepted is `authorized`, a 401 is `unauthorized`, and a 403 (a key that may lack model-list permission), a redirect, or an offline or failing provider leaves `configured`. A key is sent only to HTTPS or loopback HTTP. Docker Agent has no offline way to do this: `docker-agent models` lists a static catalog for any key. A release without `doctor` falls back to AO's own key lookup. Native ACP `host-credentials` checks configuration availability, not remote token validity.

A custom config path must be set before launching AO: project environment settings cannot override reserved `AO_*` keys. New Chat task admission checks the effective launch environment and rejects a relative, nonexistent, or non-file config, or a missing config with no usable provider key, before creating the session or workspace. The global Chat probe rejects Windows; config checks run for each new task independently of cached capabilities. Binary inventory and unknown authentication are separate from Chat availability; a detected executable alone does not establish that Docker Agent can start.

AO shows Docker's mark from docker/docker-agent `docs/assets` (Apache-2.0): `docker-mark.svg` on light backgrounds and `docker-mark-white.svg` on dark. Provenance is recorded in `frontend/src/renderer/assets/agents/LICENSE-docker-agent.txt`.

Select Docker Agent and Chat when creating a task. Model refresh reads Docker Agent's native ACP configuration choices without sending a prompt, for both Harness Models and New Task. It runs in a private temporary directory under AO data, never the selected project, because starting a native session runs the config's session-start hooks. Before discovery, the fallback is `default` (the root agent's native configured model). Discovered and live Chat choices use Docker Agent's own `model:<configured-name>` values; a slash in a configured name does not identify its provider. Arbitrary provider model names and AO reasoning-effort overrides are refused. Configure those natively. Native config, tools, hooks, and project `AGENTS.md` remain intact.

AO appends private standing instructions using Docker Agent's supported `--hook-session-start` mechanism. The JSON hook result lives in a private AO data directory; its shell command contains only the quoted file path. Native hook merging retains existing hooks. Context names the actual AO worktree so tools do not default to the source repository. It is reapplied on new/load; over 32 KiB is refused rather than truncated. Native persisted history may contain prior context. This is instruction delivery, not secret storage.

Native session databases and caches live under the selected AO data directory, scoped by AO session and conversation scope. Kill/restore loads the exact native ID and replays saved history. Unknown IDs and workspace mismatches fail; AO does not silently start fresh. The existing detached ACP host supports daemon reconnection and bounded process cleanup.

Permissions preserve native tools and user rules: AO default maps to native `default`; AO auto maps to native `balanced` (classifier-safe calls may run, others ask); bypass maps to native `autonomous` (native deny rules/guards still apply). AO accept-edits is refused because native tool annotations cannot establish that policy. Approve, reject, cancel, and turn interrupt use the ordinary ACP approval channel. Explicit native allow rules can already authorize tools, as in Docker Agent itself.

AO terminal mode, TUI/Chat handoff, reviewer support, steering, fork, and rollback are not claimed. Generic ACP exposes native commands (including compaction) and negotiated image/embedded-context/input transport; those optional surfaces were not independently exercised by the text/shell qualification. Qualification used the released Linux amd64 artifact SHA-256 `791fa6bac9f829847f00ab948f838bf54d11e0830988a5e5bce88d65ea65f2d1`, native custom OpenAI-compatible Z.ai `glm-5.3-flash`, permission controls, file edits, private instruction refresh, persisted load, and executing-shell cancellation. Routine tests run only in PR CI under the authorized VPS policy; real AO proof and capture are recorded separately in the integration report.
