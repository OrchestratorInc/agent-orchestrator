These examples use capabilities shipped in the current Go daemon and Electron desktop app. They do not rely on the retired TypeScript plugin configuration or an `examples/` directory.

## Start A Focused Chat Worker

1. Add a local GitHub repository in the desktop app.
2. Create a task named **Fix settings validation**.
3. Select an installed Chat-capable harness such as Codex or Claude Code.
4. Choose **Chat** and use a bounded prompt:

```text
Reproduce the invalid settings error, add a regression test, and make the smallest fix.
Run the focused tests and summarize changed behavior. Do not refactor unrelated settings code.
```

Watch provider activities and changed files in Chat. If an approval or structured question appears, answer it in the timeline.

## Use A Native Terminal UI

Create another task and choose **Terminal UI**. AO creates the worktree and launches the harness's native interface through native PTY hosts on macOS/Linux (tmux for legacy/fallback) or ConPTY on Windows.

Use the desktop terminal for native interactive commands. Send normal follow-up guidance through AO's message controls:

```text
The failing case is on Windows path normalization. Keep the Unix behavior unchanged.
```

## Switch Claude Code Or Codex To Chat

For a compatible idle TUI session, choose **Switch to chat UI**. AO stops the old controller, resumes the provider conversation through the native Chat driver, and keeps the same session and worktree.

If the session is busy, choose deliberately:

- **Finish work, then switch** waits for accepted work to finish before switching.
- **Stop now and switch** cancels the active turn before switching.

Switching preserves provider context, but a first TUI-to-Chat switch does not reconstruct old terminal screen output as structured Chat cards.

## Claim An Existing Pull Request

The optional CLI can start a worker and associate an existing pull request:

```bash
ao spawn --project my-project --agent codex --name "Finish PR 142" --claim-pr 142
```

Or attach a pull request to an existing session:

```bash
ao session claim-pr 142
# From outside the worker, target it explicitly:
ao session claim-pr <session-id> 142
```

The shorter form reads the current worker from `AO_SESSION_ID`.

AO observes GitHub PRs or GitLab MRs and displays their normalized facts. A claim only attaches ownership metadata; it does not check out the PR branch. Prepare the correct branch separately before implementation.

## Run A Reviewer

Open a session with a linked pull request, go to **Reviews**, select a configured reviewer harness, and start a review. Reviewer runs are separate from worker harness configuration. See the [agent catalog](/plugins/agents) for reviewer support. Enable the session auto-review toggle if you want reviews on eligible PR heads while the worker is idle; merge remains explicit.

Inspect the result, then send actionable findings to the worker. Keep human review in the loop before merging.

## Preview A Web App

Start the development server in the session worktree, then select it explicitly:

```bash
ao preview http://127.0.0.1:5173
```

For a repository with `.ao/launch.json`:

```bash
ao preview start
ao preview status
```

Open the Browser tab in the session inspector. Preview targets are session-scoped; AO does not auto-discover one when a worker starts.

Use the Browser toolbar to annotate the rendered page and send the annotation to Chat, open DevTools, or pop out the view. Choose a named profile only when you intend to reuse its saved cookies/storage; the default temporary profile remains session-isolated. Browser settings manage profiles, supported imports, and downloads.

To reuse a login, open **Settings → Browser**, create a named profile, then select it in the session Browser toolbar before signing in. To import from Chrome, Firefox, or Safari, use **Import** in that settings page and review what the dialog says is supported on your OS. AO copies selected source data into its own profile and does not edit the source browser. Import is not guaranteed to transfer every cookie or login; sign in again if a site still asks. **Clear** empties a saved profile's browsing data; **Delete** removes the AO profile. Shared named profiles share cookies across sessions, so use a temporary profile for sensitive one-off work.

## Use Browser Controls From An Agent

When the Browser tab is attached to the session, the optional CLI exposes commands such as:

```bash
ao browser snapshot
ao browser click <ref>
ao browser fill <ref> "hello"
ao browser screenshot
```

Temporary network-metadata capture must be started explicitly and expires automatically. It omits request and response bodies plus sensitive values.

## Pair The Mobile App

1. Open desktop settings and choose **Connect Mobile**.
2. Scan the pairing QR from the mobile app; it fills the host, port, connection password, and any secure transport mode automatically.
3. Treat the QR as a bearer credential and do not share it or screenshots of it. Rotate the connection password in desktop settings if it is exposed.
4. Create or open a session from the phone.

Use direct LAN access only on a trusted network. Wait for a ready QR; available secure remote endpoints can be added to its offer as setup completes. See [Connect Mobile](/configuration/remote-access). Turning it off closes the authenticated listener.

## Useful CLI Checks

The CLI talks to the already-running daemon:

```bash
ao status
ao session ls
ao session get <session-id>
ao send --session <session-id> --message "Run the targeted test and report the result."
```

The desktop app remains the recommended control surface.

For reusable project work, create an agent Cue such as `ao cue create --project my-project --name "Check tests" --prompt "Run relevant tests and summarize failures"`, then choose **Run a cue** from a session. Use `--command "npm test"` instead of `--prompt` for an exact command in a fresh local shell.

For recurring work, create an **Automation** with a project, prompt, and schedule; inspect each run in Automations. [Lifecycle automation](/configuration/lifecycle-automation) includes a daily CLI example. For projectless notes, use `ao spawn --standalone --agent codex --name notes`.

Workers can use `ao report "Tests passed; ready for review"` to report to an existing orchestrator and the command's artifact flags to attach outputs. Chat also exposes provider-supported skills, MCP tools, model/effort controls, and compaction actions.

## Standalone work, reports, and recovery

For a task without a repository, choose **New task → Standalone** and pick an agent, or run:

```bash
ao spawn --standalone --agent codex --name notes --prompt "Draft release notes"
```

AO creates a managed plain directory. Standalone work has no Git branch or PR claim, so move any output you want to keep into a real project before cleaning up the session. Project, branch, issue, PR, and orchestrator flags cannot be combined with `--standalone`.

When an orchestrator already exists, a worker can send a checkpoint with `ao report "Focused tests passed"`. Use `ao report --done --note "Ready for review" --artifact ./test-results.txt` to include a file. Reports route to that existing orchestrator; they do not create one. If the orchestrator is unavailable, inspect the CLI error and the worker's session instead of assuming the report was delivered. A human can steer active Chat work with the session message controls or `ao send --session <id> --message "Check the Windows case"`; use `--steer` only when the active-turn behavior is intended.

If the agent stops but the session remains, use **Resume agent** or `ao session resume-agent <id>`. If the entire session was terminated, use **Restore** or `ao session restore <id>` when offered. `ao session exit-agent <id>` stops only the controller; `ao session kill <id>` terminates the session. Recovery depends on the harness and persisted native state, and terminal screen output is not reconstructed as Chat history. Check for uncommitted files before cleanup; AO does not force-delete a dirty registered worktree.
