title: GitHub issue intake
description: Opt-in, assignee-scoped worker creation from GitHub issues.
---

This guide uses the GitHub tracker and your existing GitHub authentication. GitLab is also supported; select the provider explicitly for issue spawning or intake and follow [GitLab authentication](/plugins/scm).

## Configure intake

Intake needs two opt-ins, and both default to off: enable it on the daemon and configure a project with an assignee filter. Each matching issue can start a worker session, so use the filter to limit which issues AO handles.

For the desktop app, add `AO_TRACKER_INTAKE=on` to the environment your login shell exports, such as `~/.zshrc`, then relaunch AO. The app passes that environment to its daemon. For a standalone daemon, set the variable in its launch environment and restart it.

Then configure the project. `ao project set-config` replaces the full project config, so read the [full-config warning](/configuration/projects#update-from-the-cli) before using it.

```bash
ao project set-config my-app \
  --tracker-intake \
  --tracker-repo owner/repo \
  --tracker-assignee alice
```

The provider defaults to `github`. When the repository is omitted, AO can derive it from the project's Git remote. Use `ao project get my-app --json` to inspect the stored configuration.

If `AO_TRACKER_INTAKE` is unset, the project config is still stored and validated, but no sessions are spawned. The daemon logs a warning at startup naming how many projects have intake configured while the flag is off.

For one GitLab issue without enabling intake, use `ao spawn --project my-app --name issue-42 --tracker-provider gitlab --issue 42`.

## Current boundary

Matching issues may create sessions and provide issue context. The current intake path is read-only: it does not post comments, assign workflow states, or close issues after a session finishes. PR and CI observation belongs to AO's separate [GitHub SCM capability](/plugins/scm/github).
