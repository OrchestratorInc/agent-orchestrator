---
title: Source control and pull requests
description: GitHub and GitLab source-control observation, authentication, and actions.
---

AO observes GitHub pull requests and GitLab merge requests associated with active sessions and feeds normalized facts into lifecycle and desktop views. Provider-specific review and check semantics can differ.

The provider tracks:

- pull request identity and state;
- check status and failing check names;
- mergeability and merge-conflict reasons;
- review decisions and unresolved human-review comment counts.

For GitHub, authenticate `gh`. For GitLab, the daemon resolves `AO_GITLAB_TOKEN`, then `GITLAB_TOKEN`, then authenticated `glab` credentials. Use an account with access to the repository and the actions you intend to perform.

GitLab.com is allowed by default. Self-managed GitLab hosts require comma-separated `AO_GITLAB_ALLOWED_HOSTS` entries (optionally including ports); `AO_GITLAB_HOST_TOKENS` accepts comma-separated `host=token` overrides when needed. These are daemon environment settings, not project plugin blocks. Restart a desktop-owned daemon after changing its launch environment. Never put tokens in project JSON or documentation examples.

Use a full repository-host URL when a numeric PR/MR reference is ambiguous. `canonicalRepoURL` can explicitly trust an upstream for claims without changing checkout/push origin. Claiming records ownership; it does not check out the PR/MR branch. AO dispatches merge actions to the owning provider, but do not assume every GitHub review operation has identical GitLab behavior.

See [GitHub SCM](/plugins/scm/github) for authentication and the current action surface.
