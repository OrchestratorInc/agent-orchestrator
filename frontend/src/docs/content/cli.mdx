The `ao` CLI is a thin client for the local desktop app's daemon. Commands that operate on projects and sessions require the app and its daemon to be running. `ao start` opens or downloads the app, `ao status` inspects daemon state even when it is stopped, and `ao doctor` checks the local environment without requiring a running daemon. Run `ao <command> --help` to see flags supported by your installed version.

## Run the CLI

The desktop app bundles the CLI and does not add it to your PATH. Until you link it, run it by its full path. On macOS:

```bash
"/Applications/Agent Orchestrator.app/Contents/Resources/daemon/ao" status
```

On Windows and Linux the binary is `daemon/ao` (`ao.exe` on Windows) inside the app's `resources` folder.

To use the short `ao` name in any terminal on macOS or Linux, open **Settings → General**, turn on **Developer mode**, and choose **Link** beside **Global ao command**. The link stays up to date with the app. On macOS, move the app to Applications before linking; an AppImage install cannot be linked. Sessions that Orchestrator starts already have `ao` on their PATH.

To have a coding agent run these commands for you, see [Set up with your coding agent](/guides/agent-setup).

## Command tree

```text
ao
├── start                         Open the desktop app (download it when needed)
├── stop                          Stop the local daemon
├── status                        Show daemon health
├── serve                         Run the daemon without the desktop app
├── service                       install, status, uninstall (keep serve running)
├── setup                         Set up the daemon, agent, GitHub and project in one command
├── doctor                        Check the local Orchestrator environment
├── agent ls                      List built-in agent adapters and readiness
├── project                       add, ls, get, set-config, rm
├── spawn                         Create a worker or orchestrator session
├── task                          start, status, wait: hand off a task and check it started
├── session                       ls, get, kill, restore, rename, cleanup, delete,
│                                 claim-pr, exit-agent, resume-agent
├── automation                    create, list, get, update, delete, runs
├── cue                           create, list
├── report                        Report worker progress or artifacts
├── orchestrator ls               List orchestrator sessions
├── send                           Send a message to a session
├── pr                             merge, resolve-comments
├── review                         ls, trigger, cancel, submit
├── preview                        select/clear a target; start, status, stop a server
├── browser                        Control the selected session browser
├── remote-host                    status, enable, disable, link
├── import                         Import projects from legacy product data
├── completion                     Generate shell completions
└── version                        Print build information
```

This reference omits internal commands such as `daemon`, `hooks`, `launch`, `agent-process`, and `pty-host`. `ao dev` is a developer launcher; see the repository development guide for source builds.

## Desktop and daemon

For a new installation, download the desktop app from the [installation guide](/installation). The frozen npm package is a legacy launcher, not the current distribution channel.

### `ao stop`

| Flag | Purpose |
| --- | --- |
| `--timeout <duration>` | Maximum time to wait for shutdown. |
| `--json` | Print the result as JSON. |

### `ao status`

Reports daemon state, process identity, run-file location, health, and readiness. This command does not list sessions.

| Flag | Purpose |
| --- | --- |
| `--json` | Print structured daemon status. |

Use `ao session ls` for sessions.

### `ao serve`

Runs the Orchestrator daemon without the desktop app, for servers, scripts, and coding agents. It first checks the run file and `/readyz`: if a daemon already serves this data directory, `ao serve` reports it and exits 0 without starting another. If the run file points at a daemon for a different data directory (for example, you changed only `AO_DATA_DIR`), it exits 1 and asks you to set `AO_RUN_FILE` and `AO_PORT` too. Otherwise it starts the daemon in the background, waits until it is ready, and prints its URL.

| Flag | Purpose |
| --- | --- |
| `--port <n>` | Loopback port for a new daemon. Defaults to `AO_PORT`, else `3001`. Ignored, with a warning, when a daemon is already running. |
| `--background` | Start the daemon in the background and return once it is ready. This is the default; the flag exists for scripts that name it. |
| `--foreground` | Run the daemon in this process, or watch the one already running, until no daemon is left (for launchd, systemd, or a terminal). |
| `--timeout <duration>` | How long to wait for a background or still-booting daemon to become ready. A `--foreground` daemon run in this process starts without this limit. Default `2m`. |
| `--json` | Print the result as JSON. |

With `--json`, `ao serve` prints one object. Scripts can rely on these fields; new fields may be added, but none are renamed or removed:

```json
{
  "status": "ready",
  "port": 3001,
  "pid": 12345,
  "url": "http://127.0.0.1:3001",
  "reused": false,
  "runFile": "/Users/you/.ao/running.json",
  "dataDir": "/Users/you/.ao/data"
}
```

`reused` is `true` when an existing daemon was found. With `--foreground`, the object is printed only when `ao serve` reuses or follows a daemon. When it runs its own daemon in the process it prints nothing, so scripts should read the result from the default background mode. A failure exits 1 with the reason on stderr. With `--foreground`, a daemon that cannot take the data-directory lock because another Orchestrator process holds it exits 75. A bad flag exits 2.

When you open the desktop app while this daemon runs, the app swaps in its own daemon on the same data directory. Because it replaced a headless daemon, the app keeps that one running after it quits. A daemon the app starts when no `ao serve` daemon is running quits with the app, and the service section below covers that case. Stop either with `ao stop`.

With `--foreground`, `ao serve` stays running for as long as a daemon serves the data directory, following the app's swap. It exits 0 after a clean stop such as `ao stop`, and 1 when the daemon crashed or was the desktop app's own and quit with the app, so a service manager starts a new one.

Usage analytics follow the desktop app: on by default, never code, prompts, or conversations. They stay off when you turned off **Share usage analytics** in the app, when `DO_NOT_TRACK=1` or `AO_TELEMETRY_REMOTE=off` is set, and in development builds.

### `ao service`

Keeps `ao serve` running across logins and reboots, as a user service that never needs `sudo`. On Linux it keeps running while you are logged out only with lingering; see below.

| Command | Purpose |
| --- | --- |
| `ao service install` | Write the service, start it, and wait until the daemon is ready. |
| `ao service status` | Show whether the service is installed and loaded, and the daemon's state. |
| `ao service uninstall` | Stop the service and remove the file `install` wrote. |

| Platform | Service |
| --- | --- |
| macOS | launchd user agent `~/Library/LaunchAgents/dev.agent-orchestrator.serve.plist` |
| Linux | systemd user unit `~/.config/systemd/user/agent-orchestrator-serve.service` |
| Windows | Not supported yet. Run `ao serve` from a logon task instead. |

The service runs `ao serve --foreground` with the `PATH`, `AO_DATA_DIR`, `AO_RUN_FILE`, `AO_PORT`, `DO_NOT_TRACK`, and `AO_TELEMETRY_*` values of the shell you install from, so the daemon finds the same agents and tools. Run `ao service install` again after changing them. A custom `AO_DATA_DIR` or `AO_RUN_FILE` gets its own service name, so it never replaces your main one. The service restarts the daemon if it crashes; `ao stop` stops it until the next login. When a daemon is already running for the same data directory (for example, the desktop app's), the service watches it instead of starting a second one, and starts its own if that daemon crashes or quits with the app. Because the service cannot tell `ao stop` from the app quitting, stopping the desktop app's own daemon also makes the service start one; run `ao service uninstall` first to keep Orchestrator stopped. `install` and `uninstall` only touch a file that `ao service install` wrote. If the self-hosted host setup script already installed its own service (`dev.aoagents.self-hosted` / `ao-self-hosted.service`) for the same data directory, `install` refuses and prints how to remove it, since that service already keeps the daemon running.

`install` accepts `--port`, `--no-wait`, `--timeout`, and `--json`; `status` and `uninstall` accept `--json`. On Linux, a user service starts when you log in and stops when you log out unless lingering is on; `install` and `status` report it (`"linger"` in `--json`) with the command to turn it on, `loginctl enable-linger <user>`. On a headless server, turn it on so the service runs from boot. `journalctl --user -u agent-orchestrator-serve` shows early `ao serve` failures for the default service; for a custom `AO_DATA_DIR` or `AO_RUN_FILE`, use the name `ao service status` prints.

### `ao setup`

Takes Orchestrator from installed to ready for a task in one command. It is built for coding agents asked to "set up Orchestrator", and works the same from a terminal.

```bash
ao setup --path ~/code/my-app --json
```

It runs these steps in order and reports each as `{step, status, detail, fix}`, where `status` is `ok`, `fixed`, `skipped`, `needs_human`, or `failed`:

| Step | What it does |
| --- | --- |
| `daemon` | Reuses the daemon serving this data directory, or starts one in the background the same way `ao serve` does. |
| `agent` | Picks the agent: `--agent` if given, otherwise the coding agent running the command (detected from its environment, `AI_AGENT` first), otherwise the first ready agent. Checks that it is installed and signed in. It never installs an agent or signs one in. |
| `github` | Checks that the GitHub CLI is signed in. It never runs `gh auth login`. |
| `project` | Registers `--path` (default: the Git repository containing the current directory) with the chosen agent for workers and the orchestrator, or reuses its registration. A repository with no remote gets its checked-out branch as the default branch, as `ao project set-config --default-branch` would. |
| `first-run` | Reports that a registered project makes the desktop app skip its first-run screens. |
| `start` | Only with `--start "<task>"`: starts the task as `ao task start --wait` does, on the project's orchestrator or, with `--worker`, on one worker. |
| `verify` | Sums up: `ready` is true when nothing is left to do. |

| Flag | Purpose |
| --- | --- |
| `--path <repo>` | Repository to register. |
| `--agent <id>` | Agent to use. `--worker-agent` and `--orchestrator-agent` override one role. |
| `--start "<task>"` | Start this task once setup is ready. Add `--worker` for a single worker. |
| `--yes` | Replace agents already saved on a registered project with the ones you passed. Without it, setup keeps them and reports `needs_human`. |
| `--check` | Report what is set up and what is missing. Changes nothing and never starts the daemon. |
| `--dry-run` | Show what setup would do, without changing anything. |
| `--json` | Print one object: `{ready, agent, project, steps, next_actions, task}`. |

| Exit code | Meaning |
| --- | --- |
| `0` | Ready, and the task started when `--start` was given. |
| `10` | A person must act first. `next_actions` lists the exact commands, such as the agent's login command or `gh auth login`. With `--check`, also when `ao setup` still has work to do. |
| `1` | A step failed, or the task started with `--start` failed. |
| `2` | Usage error. |
| `3` | The task started with `--start` is waiting on you. |

```json
{
  "ready": false,
  "agent": { "id": "claude-code", "source": "caller", "detectedFrom": "CLAUDECODE", "authStatus": "unauthorized", "worker": "claude-code", "orchestrator": "claude-code" },
  "project": { "id": "my-app", "path": "/Users/me/code/my-app", "defaultBranch": "main", "reused": false },
  "steps": [
    { "step": "daemon", "status": "ok", "detail": "daemon running at http://127.0.0.1:3001 (pid 4242)", "fix": "" },
    { "step": "agent", "status": "needs_human", "detail": "using claude-code (the calling agent, detected from CLAUDECODE): agent claude-code is not signed in", "fix": "run `claude auth login`" }
  ],
  "next_actions": ["run `claude auth login`"],
  "task": null
}
```

The `steps` list above is shortened. A daemon that `ao setup` starts follows the same usage-analytics setting as `ao serve`. Once setup is ready, open the app on macOS with `open "/Applications/Agent Orchestrator.app"`.

Lists the daemon's built-in agent catalog together with local installation and authentication readiness.

| Flag | Purpose |
| --- | --- |

| `--json` | Print the raw inventory response. |

### `ao project`

| Command | Purpose |
| --- | --- |
| `ao project add` | Register a local Git repository or multi-repository workspace. Pass `--default-branch <branch>` for a repository with no remote. Scratch is an Orchestrator-managed built-in project. |
| `ao project ls` | List registered projects. |
| `ao project get <id>` | Show one project and its resolved configuration. |
| `ao project set-config <id>` | Update typed per-project configuration. |
| `ao project rm <id>` | Remove a project registration. |

Focused `set-config` flags change only the fields they name and keep the rest of the saved config. `--config-json` replaces the entire project config, and its JSON decoder ignores unknown keys. See [Projects: update from the CLI](/configuration/projects#update-from-the-cli) for safe alternatives and details. This command does not edit the old `agent-orchestrator.yaml` file.

Use `ao automation create`, `list`, `get`, `update`, `delete`, and `runs` to manage recurring work. To create one, provide a project, name, prompt, and exactly one schedule: `--cron` or `--rrule`. Set `--timezone` to an IANA time-zone name such as `America/New_York`. Pause a definition with `ao automation update <id> --enabled=false`. See [schedule behavior](/configuration/lifecycle-automation#what-ao-handles).

`ao cue create --project <id> --name <name>` requires exactly one `--command` or `--prompt`. `ao cue list --project <id>` lists definitions. Editing, deleting, and invoking Cues is available in the desktop; the CLI does not have a `cue run` command.

## Sessions

### `ao spawn`

Creates a session in a registered project, or a projectless worker with `--standalone`. The command takes no positional arguments and requires a display name.

```bash
ao spawn --name fix-login --project my-app --agent codex --prompt "Fix the login regression"
```

Important flags include:

| Flag | Purpose |
| --- | --- |
| `--name <name>` | Required sidebar name, at most 100 characters. |
| `--project <id>` | Project to use. Otherwise Orchestrator resolves environment and current directory context. |
| `--agent`, `--harness <name>` | Override the project's agent. The two names are aliases. |
| `--kind worker\|orchestrator` | Select the session role. |
| `--mode chat\|tui` | Select structured Chat or the agent's native terminal UI. |
| `--branch <name>` | Branch for Git projects. Scratch projects do not support it. |
| `--prompt <text>` | Initial prompt. |
| `--standalone` | Projectless worker; requires an explicit agent and excludes project, branch, issue, PR, and orchestrator options. |
| `--model <model>` | Override the selected provider model for this spawn. |
| `--permission <mode>` | Permission mode for this spawn: `default`, `accept-edits`, `auto`, or `bypass-permissions`. A spawn from a session in the same project may choose an equal or stricter mode than the project's role setting. When the project sets none, an orchestrator cannot exceed its own mode. |
| `--tracker-provider github\|gitlab` | Select the issue provider for `--issue`. |
| `--issue <id>` | Associate a tracker issue. |
| `--claim-pr <ref>` | Claim an existing pull request after spawning. |
| `--no-takeover` | Refuse a PR already owned by another active session. |
| `--review` | Claim the PR to review it, not work on it: automatic CI and review-comment fixing and native auto-review are turned off first. Implies `--no-takeover`. Requires `--claim-pr`. |
| `--skip-agent-check` | Skip only the CLI-side install/auth preflight. |

Orchestrator chooses a project in this order: `--project`, `AO_PROJECT_ID`, the project for `AO_SESSION_ID`, then the closest registered project containing the current directory. Before spawning, Orchestrator refreshes the selected agent's readiness unless you use `--skip-agent-check`. Readiness is advisory.

### `ao task`

Hands a task to Orchestrator and reports, through its exit code, whether the agent really picked it up. It is meant for scripts and for other coding agents.

```bash
ao task start "Fix the failing login test" --wait --json
```

By default the project's orchestrator receives the task, plans it, and starts workers. With `--worker`, a single worker session takes the task directly. Without `--project`, Orchestrator uses `AO_PROJECT_ID`, then the closest (most specific) registered project that contains the current directory. It exits `2` as a usage error when no project contains it, or when several tie for the closest match.

| Command | Purpose |
| --- | --- |
| `ao task start "<brief>"` | Start the task. Flags: `--project <id>`, `--worker`, `--agent <id>` and `--base <branch>` (only with `--worker`), `--wait`, `--timeout <duration>` (default `120s`), `--json`. |
| `ao task status <task-id>` | Report the task's status once. Supports `--json`. |
| `ao task wait <task-id>` | Wait until the task has started, failed, or needs you. Supports `--timeout` and `--json`. |

`start --wait` behaves like `start` followed by `wait`. A status read that fails for a passing reason, such as the daemon being briefly unreachable, doesn't end a wait; it keeps polling within `--timeout`. A task has started once its turn has finished, or has stayed running for a few seconds before `--timeout` ends. `wait` confirms that the task started, not that it finished, so an approval the agent asks for later is not seen by that call: keep calling `ao task status` or `ao task wait` until it reports `done`, `failed` or `needs_input`. For a terminal (TUI) task this works when its agent records turns (Claude Code does); otherwise check the session with `ao session get <id>`. Before starting, Orchestrator checks that each agent involved is signed in, and stops if one definitely is not. Without `--worker`, `--agent` and `--base` exit `2` as a usage error, because the orchestrator chooses agents and branches for its workers; set project defaults with `ao project set-config` instead.

For a task sent to the orchestrator, the status includes the workers it started: `needs_input` if any of them needs you, `running` while the orchestrator or any worker is still working, `failed` if a worker failed after the orchestrator's turn ended, and `done` only when the orchestrator and all its workers have finished. Each worker is read at the turn it is running now (otherwise its latest), so follow-up work the orchestrator sends it keeps the task `running`, and an approval on its running turn reads `needs_input` even when a follow-up is queued. A worker that cannot be read keeps the task `running`. After a retry of the orchestrator's turn, only the current attempt's workers can fail the task. Workers that existed before the task are not tracked. A terminal (TUI) worker is read from its recorded turns too; one whose agent records none never reads `done`, so the task stays `running`.

| Exit code | Meaning |
| --- | --- |
| `0` | With `--wait` or `ao task wait`: the task started, running or done. A one-shot read (`ao task status`, or `start` without `--wait`) also exits `0` while the task is `starting` or `queued`, so check `status`. |
| `1` | The task failed: the session could not start, or the agent's turn failed. Also a lookup that cannot succeed, such as a 404 for the session (this ends `ao task wait` too), or a status read that failed outside a wait. Transient read errors during a wait are retried within `--timeout`. A failed read does not prove the task failed, so when `taskId` is set, check it with `ao task status` before submitting again. |
| `2` | Usage error: the command itself needs fixing. It prints no JSON. |
| `3` | The task is waiting on you, for example for an approval. Answer it in Orchestrator; starting the task again would run it twice. |
| `4` | The task was submitted but the wait ended before it was confirmed: `--timeout` ran out (still queued, still starting, workspace setup unfinished, or running for under 5 seconds), or the wait was interrupted (Ctrl-C, SIGTERM, a caller's timeout). The output still has the `taskId`; don't start the task again, follow it with `ao task wait`. |

With `--json`, the command prints one object:

```json
{
  "status": "failed",
  "taskId": "my-app-3",
  "sessionIds": ["my-app-3"],
  "reason": "Not logged in · Please run /login (auth_required)",
  "fix": "run `claude auth login`, then retry"
}
```

`status` is `starting`, `queued` (accepted; runs after the agent's current turn), `running`, `done`, `failed`, or `needs_input`. `taskId` is what you pass to `ao task status` or `ao task wait`:

- a worker task: the worker's session ID;
- a task sent to a Chat orchestrator: `<orchestrator-session>:<turn>`;
- a task sent to a terminal (TUI) orchestrator: `<orchestrator-session>:tui-<unix ms>-<length>-<hash>`, the first turn that session recorded from when the brief was sent that carries this brief (other work recorded after the send is never taken for it, and session activity alone never confirms it);
- empty when no task id could be reported. That does not prove no task exists: if the reason says the daemon accepted the task without a turn id, or that delivery could not be confirmed, check the session with `ao session history <id>` before starting it again.

For `needs_input`, `fix` names the session that owns the pending request: the orchestrator when its own turn asks, or the worker when a tracked worker asks. Answer in the session `fix` names.

A terminal (TUI) session is judged by the turns its agent records, as `ao session history` shows them (Claude Code records them): a task reads `done` once its turn is recorded with a reply, even if it finished between polls. For a terminal orchestrator, `done` confirms its own turn only; its history has no records of the workers it started, so check those with `ao session ls`. A terminal orchestrator that was just started gets about 15 seconds to boot before the brief is typed in; if the brief still lands unsubmitted, the command exits `4` with the task id, and you submit it in that session rather than starting the task again. A terminal session whose agent records no turns only shows idle or working, so it is never `done`; if `ao task wait` sees it working and then back at its prompt, it reports `running`. If the wait times out, the reason says which case it was. `sessionIds` lists the session that runs the task and any workers the orchestrator started for it; their state is part of `status`. A task that finished stays `done` after its session or a worker is archived; only a session archived before its turn finished makes it `failed`. A chat task id whose turn is not in the session's history fails once the CLI has read back to the start of that history; until then it reads `starting`. When the agent is not signed in, `fix` gives the agent's own login command. `ao spawn`, `ao send`, and the session states are unchanged.

### `ao session`

| Command | Purpose |
| --- | --- |
| `ao session ls` | List active worker sessions. Use `--all` for orchestrators and `--include-terminated` for history. |
| `ao session get <id>` | Show one session. |
| `ao session kill <id>` | Terminate a session. Dirty workspaces are preserved. |
| `ao session restore <id>` | Relaunch a terminated session when recovery is supported. |
| `ao session exit-agent <id>` | Stop the controller while retaining the session. |
| `ao session resume-agent <id>` | Start the controller again in that session. Also retries a session that failed to start. |
| `ao session rename <id> <name>` | Change its display name. The project orchestrator cannot be renamed. |
| `ao session cleanup` | Reclaim eligible terminated workspaces; supports `--dry-run`. Workspaces already released are not listed again. |
| `ao session delete <id>` | Permanently delete a terminated session and its AO history once its worktree is cleaned up; `--cleanup` cleans it up first, never forced; `--keep-artifacts` keeps its artifact files, view only, on the Artifacts page. Branches, PRs and agent account usage totals are kept. |
| `ao session claim-pr [<session-id>] <pr-ref>` | Attach an existing PR; omitting the session uses `AO_SESSION_ID`. `--review` claims it to review: automatic CI and review-comment fixing and native auto-review are turned off first, and it never takes the PR from another active session. `--review=false` turns fixing back on to take it over. |

Most lookup commands accept `--project` to disambiguate a session ID.

Claiming a PR records ownership and starts observation. It does not check out the PR branch, so prepare the right branch or worktree separately. **Archive** ends the session. Exit and resume stop or start only its controller. Closing a view does neither.

### `ao send`

Sends a message through the daemon to a running session.

```bash
ao send --session ao-123 --message "Please address the failing test"
```

`--session` and `--message` are required for ordinary sends. When called from a session with `AO_SESSION_ID`, Orchestrator prefixes the sender identity.

Use `--steer` to steer an active supported Chat turn or submit a normal turn when idle. `--client-message-id` supplies a stable delivery handle. If delivery is uncertain, recover the recorded result without resending:

```bash
ao send --session <session-id> --steer --recover-only --client-message-id <handle>
```

`--recover-only` requires `--steer` and a handle; it does not require a new message or contact the provider. A receipt confirms acceptance state, not that the agent completed the instruction.

### `ao orchestrator ls`

Lists orchestrator sessions. Add `--json` for structured output.

Inside a worker, `ao report "Progress summary"` sends a report to its existing orchestrator. Reporting requires `AO_SESSION_ID`; it does not create an orchestrator or claim a PR.

Needs-input reports are sent immediately. Stuck reports may interrupt or combine with other reports. Done reports wait five minutes before delivery; ordinary checkpoints can wait up to one hour.

For a structured report, choose one state flag: `--checkpoint`, `--needs-input`, `--stuck`, or `--done`. Include `--note` with it. `--note` and free-form text are each limited to 1000 characters. Attach reviewable deliverables with `--artifact`, `--pr-created`, or `--pr-reviewed`; pull-request flags require full URLs. Do not combine free-form text with structured state or output flags.

```bash
ao report --done --note "Focused tests passed"
```

`ao report` must run in a worker environment that provides `AO_SESSION_ID`.

## Preview and browser control

### `ao preview [url]`

Selects what the desktop Browser panel displays for the session identified by `AO_SESSION_ID`. With no argument Orchestrator looks for a supported static entry point in the session workspace; with a file or `file:`, `http:`, or `https:` target it opens that target.

| Command | Purpose |
| --- | --- |
| `ao preview clear` | Clear the selected preview. |
| `ao preview start [configuration]` | Start exactly one command from `.ao/launch.json`, wait for readiness, and select it. |
| `ao preview status` | Show the managed preview process and recent bounded logs. |
| `ao preview stop` | Stop the managed process tree. |

`.ao/launch.json` is optional project configuration. Orchestrator does not infer or scaffold development servers, and static files do not require one.

### `ao browser`

Controls the live, session-isolated Electron browser owned by the desktop app. It also resolves its target from `AO_SESSION_ID`; the desktop app must be open.

Browser commands include status and open, page snapshots, click/drag/fill/type, scrolling, tabs and popups, DevTools, screenshots, console and page errors, and optional network metadata capture. Run `ao browser --help` for the full command list.

An element reference becomes stale when navigation or a frame or tab change replaces the page. Take a new snapshot when Orchestrator reports `STALE_REFERENCE`.

The first `ao browser snapshot --delta` returns the full page tree. Later calls return only changes; add `--full` to request the full tree again. The `--annotate` option on screenshots labels interactive elements with references.

`click` and `drag` accept `--human` for pages that ignore instant pointer movement. Keep the Browser panel visible when using `--human` or taking screenshots. Hidden or covered windows stop painting, so these commands time out.

Network capture is off by default. When enabled, it records bounded metadata only, excludes request and response bodies and sensitive values, and expires automatically.

## Remote access

### `ao remote-host`

Lets your other devices use this machine through its authenticated remote listener.

| Command | Purpose |
| --- | --- |
| `ao remote-host status` | Show the host ID, addresses, and whether the address is fixed. Add `--show-password` to also print the pairing password; treat that output as a credential. |
| `ao remote-host pair` | Print the address and a one-time pairing code. One device can use it, within 10 minutes, and gets its own token. |
| `ao remote-host devices` | List the devices that can reach this machine. `devices revoke <ID>` revokes one; `devices revoke --all` revokes every device and unlinks the account. |
| `ao remote-host require-device-credentials on\|off` | Stop accepting the pairing password, so each device needs its own token or the linked account's. |
| `ao remote-host enable` | Turn on remote access. `--tunnel-only` serves it only through a Cloudflare tunnel; `--tunnel` keeps the LAN listener too. |
| `ao remote-host disable` | Turn off remote access. Sessions keep running. |
| `ao remote-host link` | Add this machine to your AO account: it prints a sign-in link and a QR code, and waits up to 5 minutes for you to sign in from any device. The machine then gets a fixed address and appears on every device signed in to the account. `--label` sets its name (default: the name the account already has for it, else the hostname); `--no-qr` prints only the link. On a LAN-only listener it adds a Cloudflare tunnel, as `--tunnel` does. |

`link` is how a VM or other machine without the desktop app joins your account. See [Connect a VM or other headless machine](/configuration/remote-access#connect-a-vm-or-other-headless-machine).

## Environment

| Variable | Default | Purpose |
| --- | --- | --- |
| `AO_PORT` | `3001` | Loopback daemon port. |
| `AO_RUN_FILE` | `~/.ao/running.json` | Daemon identity and port handshake. |
| `AO_DATA_DIR` | `~/.ao/data` | Daemon data directory. |
| `AO_REQUEST_TIMEOUT` | `60s` | REST request timeout. |
| `AO_SHUTDOWN_TIMEOUT` | `10s` | Graceful shutdown limit. It also scales how long a starting daemon waits for a previous daemon to release the data directory (9 × this + 18 s). |
| `AO_SESSION_ID` | unset | Current session context for preview, browser, and in-session calls. |
| `AO_PROJECT_ID` | unset | Current project context for spawn resolution. |

All current Orchestrator application state stays under `~/.ao` unless `AO_DATA_DIR` or `AO_RUN_FILE` overrides it. The one file outside it is the service definition that `ao service install` writes, which holds no state.

## Report a problem

Unreleased: `ao triage` collects bounded, redacted diagnostics and opens Claude Code
or Codex to help draft a report, even with the daemon down. Files go under
`$AO_DATA_DIR/triage` when set, otherwise `~/.ao/triage`. After the agent exits,
review the text and answer `[y/N]` before posting. Use `--no-launch` to prepare
files only, or `--agent claude|codex` to choose an installed agent.
