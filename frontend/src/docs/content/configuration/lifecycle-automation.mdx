title: Lifecycle automation
description: How AO currently routes CI failures, review feedback, and merge conflicts to the correct session.
---

AO has built-in lifecycle automation. It is not currently a user-configurable `reactions:` schema: YAML keys such as `retries`, `escalateAfter`, `auto-merge`, and notifier routing belong to the retired implementation and are not accepted by current project configuration.

## What AO handles

| Observation | Current behavior |
| --- | --- |
| Failing CI checks | Sends the failing check names and links to the owning session |
| Changes requested or unresolved review comments | Sends focused unresolved feedback to the owning session |
| Merge conflict | Asks the eligible session to rebase and resolve it |
| PR ready to merge | Creates a durable in-app notification |
| PR merged or closed | Updates session facts and creates/resolves notifications |
| Session needs input | Creates a durable notification for human attention |

Messages are signature-deduplicated, so an unchanged set of failures or comments is not sent on every poll. A changed failure set or changed unresolved feedback can produce a fresh nudge.

Recurring **Automations** are separate from these event reactions. In the sidebar, create a definition with a project, prompt, harness/role, timezone, and schedule; inspect its run history, edit it, pause/resume it, or delete it. The CLI supports the same stored definitions:

```bash
ao automation create --project my-app --name "Daily checks" \
  --prompt "Run the project checks and summarize failures" \
  --cron "0 9 * * *" --timezone UTC
ao automation list --project my-app
ao automation runs <automation-id>
ao automation update <automation-id> --enabled=false
```

Use exactly one supported five-field cron expression or RRULE, with an IANA timezone. Cron accepts numeric minute/hour, `*` for day-of-month/month, and a supported weekday selection; arbitrary cron ranges/steps are not accepted. RRULE rejects `COUNT`/`UNTIL` and intervals faster than one minute. It runs in the local daemon, so it cannot dispatch while the host is asleep or AO is stopped. On recovery it catches up at most three missed occurrences; runs of the same definition are coordinated to avoid overlapping dispatch. Deleting a definition also deletes its run history.

For a first run, create one definition in **Automations** with a short prompt and a schedule a few minutes ahead, then open its run history and linked session. If nothing runs, verify the timezone, that the definition is enabled, and that the desktop/daemon stayed awake. Pause the definition before changing a schedule you are still testing. After a restart, AO catches up at most three missed occurrences; it does not replay every missed time slot.

Project **Cues** provide reusable instructions or exact shell commands for manual invocation, not schedules. An agent Cue targets an eligible session or starts a worker; a command Cue opens a fresh local terminal. Manage these from the project Cues dialog and use **Run a cue** in a session.

For example, add an agent Cue named **Check tests** with the prompt `Run the focused tests and report failures`, then use **Run a cue** from a project session. If that session cannot accept a prompt, choose the offered new-worker path or wait for it to become eligible. A command Cue such as `npm test` runs that exact command in a fresh local shell; it is not reviewed or interpreted by an agent, so check the command and working context before running it.

## Mode-aware delivery

Lifecycle messages go through the same session manager as user messages:

- Terminal UI sessions receive the message through their runtime.
- Chat sessions receive a native provider turn and persist it in the structured conversation.

AO does not run both controllers at once. A handoff between compatible interfaces drains or interrupts the old controller before committing the new one.

## Notifications

The desktop notification center keeps durable read/unread history for input requests, merge-ready PRs, merged PRs, and PRs closed without merging. Electron also shows an app toast while the app is running. Marking read retains history; clear-one and clear-all remove records from the center. Paired phones can receive push notifications when their permissions, device mute setting, and daemon connectivity allow.

AO does not currently configure Slack, Discord, webhook notifiers, per-reaction retry budgets, or automatic merge from project config. Merge explicitly from the desktop or with:

```bash
ao pr merge <pr-number>
```

## Reviews

SCM observation and AO reviewer agents are related but distinct:

- The GitHub/GitLab observer watches a claimed PR/MR and feeds CI/review/merge facts into lifecycle.
- AO review runs launch a configured reviewer agent against a worker PR. Use the desktop Reviews view or `ao review trigger`, `ao review ls`, and `ao review cancel`.

`autoReview` is a project default copied into new worker sessions; each session also has its own toggle. Automatic review waits for an eligible PR head and an idle worker. It does not automatically merge or convert every workspace inspection into a published review. Reviewer support is listed in the [agent catalog](/plugins/agents).
