Orchestrator routes CI failures, review feedback, and merge conflicts with built-in rules. Project settings do not accept the retired `reactions:` configuration. See [Migration](/migration) before reusing an old YAML example.

For a step-by-step pull-request workflow, see [Handle CI and review feedback](/guides/reactions).

## What Orchestrator handles

| Observation | Current behavior |
| --- | --- |
| Failing CI checks | Sends the failing check names and links to the owning session |
| Changes requested or unresolved review comments | Sends focused unresolved feedback to the owning session |
| Merge conflict | Asks the eligible session to rebase and resolve it |
| PR ready to merge | Creates a durable in-app notification |
| PR merged or closed | Updates session facts and creates/resolves notifications |
| Session needs input | Creates a durable notification for human attention |

Messages are signature-deduplicated, so an unchanged set of failures or comments is not sent on every poll. A changed failure set or changed unresolved feedback can produce a fresh nudge.

Recurring **Automations** are separate from these event rules. In the sidebar, create an automation with a project, prompt, agent, role, time zone, and schedule. You can inspect its run history, edit it, pause or resume it, and delete it. The CLI supports the same saved definitions:

```bash
ao automation create --project my-app --name "Daily checks" \
  --prompt "Run the project checks and summarize failures" \
  --cron "0 9 * * *" --timezone UTC
ao automation list --project my-app
ao automation runs <automation-id>
ao automation update <automation-id> --enabled=false
```

Choose one schedule format: a five-field cron expression or an RRULE, a calendar recurrence rule. Set the time zone with an IANA name, such as `America/New_York`.

Cron accepts numeric minute and hour fields, `*` for day and month, and supported weekday choices. It does not accept arbitrary ranges or steps. RRULE does not accept `COUNT` or `UNTIL`, or intervals faster than one minute.

Automations run in the local daemon, so the computer must be awake and Orchestrator must be running. After a restart, Orchestrator runs at most three missed occurrences. A scheduled automation will not start another run while its current run is active. Deleting an automation also deletes its run history.

An automation can also run **after a session ends** instead of on a schedule. Under **Runs**, choose **After a session ends**, or pass `--trigger session_ended` to `ao automation create`. It starts one new worker each time a worker in the project is archived, or ends because its PR merged. Archiving from the app, `ao session kill`, and an orchestrator all count. Daemon shutdowns, crashes, agent switches, and project removal do not start it. The new session's prompt ends with the ended session's ID, title, branch, PRs, task, and transcript path, so the agent can review what happened, for example to improve your skills or `AGENTS.md`. Reviews of different sessions can run at the same time. A session that such a run started never starts another one.

A worker started this way runs in the background, so the session you ended doesn't seem to come back. It stays off the board, the sidebar and Archive until it opens a PR or needs you. With a chat agent, AO closes the worker when its turn ends without a PR. A terminal agent can't tell AO when it's done, so it ends the session itself. Open the worker from the automation's run history. An orchestrator started this way stays visible, because it coordinates workers over many turns.

### Dreaming and instructions

**Instructions** are standing directions that Orchestrator adds to new sessions. There are two kinds, and both are edited in **Dreaming**, under **Built-in** on the **Automations** page:
- Your own apply to every new worker and orchestrator in every project.
- A project's apply to new sessions in that project.

Each set is plain text, up to 8 KB. A session keeps the instructions it started with.

**Dreaming** keeps instructions up to date. It is a built-in automation: turn it on with its switch on the **Automations** page, which adds one dreaming automation to each project. Open its row to see and edit the instructions. After each worker in that project ends, a dreaming agent reads what you typed after the opening task, and which commands the agent ran and whether they passed:
- What holds in any project, such as how you like answers or when to commit, goes into your instructions.
- Facts about the repository, such as its test command, go into the project's.

Each dream treats the instructions as everything learned so far and keeps them true and short:
- It merges duplicates, rewrites lines a newer session refined, and removes lines a newer session contradicted. It also checks the history of earlier dreams.
- It never changes a line you typed or edited. If a session contradicts one of your lines, the dream says so in its summary instead.
- It never adds back a line you deleted.
- It learns about you only from what you typed. From the agent's commands it learns only project facts, such as which test command passes. It never copies instructions from tool output, files or web pages.

Under the box you can see when dreaming last changed the text. **View session** opens the dream that made the change, and **Undo** restores the text from before it. If you save while a dream is running, your text wins and the dream retries on top of it.

Each dream runs as a standalone session, so it needs no worktree and runs no setup scripts. It also runs in the background: it doesn't appear on the board, in the sidebar or in Archive, so the session you ended stays archived. Open the latest dream from **View session** under the box. A dream appears in the sidebar only if it needs you, for example when it waits for an answer. With a chat agent, AO closes the dream when its turn ends; a terminal agent ends the session itself. If the dream's last step fails, the **Dreaming** automation shows the error. Within a project, dreams run one at a time. Every ended worker starts a dream, including workers an orchestrator started and you never talked to; from those, a dream learns only project facts. A dream runs on the same agent as the session that ended. To change what dreaming looks for, edit the **Dreaming** row. Agents can read the instructions with `ao instructions show`, but only you and dreaming can change them. That way a hostile file or web page can't plant instructions in every later session.

To try an automation, create one in **Automations** with a short prompt and a schedule a few minutes ahead. Then open its run history and linked session. If it does not run, check the time zone, confirm the automation is enabled, and make sure Orchestrator stayed open and the computer stayed awake. Pause the automation before changing a schedule you are testing.

Project **Cues** save reusable instructions or exact shell commands for manual use. They do not run on a schedule. An agent Cue sends a prompt to an eligible session or starts a worker. A command Cue opens a fresh local terminal. Manage Cues in the project dialog and choose **Run a cue** from a session.

For example, create an agent Cue named **Check tests** with the prompt `Run the focused tests and report failures`, then choose **Run a cue** in a project session. If the session cannot accept a prompt, start a worker from the offered option or wait until the session can accept one.

A command Cue such as `npm test` runs that exact command in a new local shell. An agent does not review or interpret it, so check the command and working directory before running it.

## Mode-aware delivery

Lifecycle messages go through the same session manager as user messages:

- Terminal UI sessions receive the message through their runtime.
- Chat sessions receive a native provider turn and persist it in the structured conversation.

Orchestrator does not run both controllers at once. A handoff between compatible interfaces drains or interrupts the old controller before committing the new one.

## Notifications

The desktop notification center keeps alerts for input requests, pull requests ready to merge, merged pull requests, and pull requests closed without merging. Desktop toasts appear while Orchestrator is running. Marking an alert read keeps it in history; clearing one or all removes it from the center.

Paired phones can receive push notifications when permissions allow, the device is not muted, and the daemon can connect to the push service.

Orchestrator does not currently configure Slack, Discord, webhook notifiers, per-reaction retry budgets, or automatic merge from project config. Merge explicitly from the desktop or with:

```bash
ao pr merge <pr-number>
```

## Reviews

Repository observation and Orchestrator reviewer agents are related but separate:

- The GitHub/GitLab observer watches a claimed pull request or merge request and records CI, review, and merge data.
- An Orchestrator review run starts a configured reviewer against a worker's pull request. Use **Reviews** in the desktop app or `ao review trigger`, `ao review ls`, and `ao review cancel`.

`autoReview` is a project default copied to new worker sessions. Each session also has its own toggle. Automatic review waits for an eligible pull-request revision and an idle worker. It does not merge the pull request or publish every workspace inspection as a review. See the [agent catalog](/plugins/agents) for reviewer support.
