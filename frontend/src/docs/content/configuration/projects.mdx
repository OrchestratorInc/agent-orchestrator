A project is a repository, a multi-repository workspace, or an AO-managed Scratch directory. AO stores project identity and typed configuration in its database; there is no current `agent-orchestrator.yaml` lookup or global YAML registry.

## Project kinds

| Kind | Use it for |
| --- | --- |
| Single repository | Normal Git projects; each session receives an isolated worktree |
| Workspace | A root repository plus direct child repositories managed as one project |
| Scratch | Plain-directory work without branches, PRs, or Git-only settings |

Add and manage projects from the desktop sidebar. The equivalent CLI commands are:

```bash
ao project add --path /absolute/path/to/repo
ao project add --path /absolute/path/to/workspace --as-workspace
ao project ls
ao project get <project-id>
ao project rm <project-id>
```

## Current configuration fields

Project settings expose the fields that AO consumes at spawn time:

| Field | Purpose |
| --- | --- |
| `canonicalRepoURL` | Explicit trusted upstream for numeric PR claims; does not change checkout/push origin |
| `autoReview` | Default automatic review setting copied to new worker sessions |
| `defaultBranch` | Base branch for new Git worktrees; defaults to `auto` |
| `sessionPrefix` | Prefix used in generated session identifiers |
| `env` | Extra environment variables forwarded to agent runtimes |
| `symlinks` | Repo-relative paths linked into each session workspace |
| `postCreate` | Shell commands run after workspace creation |
| `agentConfig` | Default model and permission settings |
| `worker` | Worker harness and agent-config override |
| `orchestrator` | Orchestrator harness and agent-config override |
| `agentRules` | Inline standing instructions for workers |
| `agentRulesFile` | Repo-relative rules file appended to worker instructions |
| `orchestratorRules` | Standing instructions for orchestrator sessions |
| `reviewers` | Reviewer harnesses used for AO review runs |
| `trackerIntake` | Opt-in, read-only issue intake that can spawn workers; inert unless the daemon also has `AO_TRACKER_INTAKE=on` |
| `containerReap` | Project-wide opt-out from AO's session-container cleanup |

`symlinks` and `agentRulesFile` must remain inside the repository. AO rejects absolute paths and traversal. Scratch rejects Git-only fields such as `defaultBranch` and symlinks.

`defaultBranch: "auto"` resolves each repository independently. AO selects the remote named by Git's `checkout.defaultRemote`, otherwise `origin`, otherwise the repository's only remote. It asks that remote for its symbolic `HEAD`, fetches the exact advertised branch, and can fall back to the same remote's cached `HEAD` while offline.

AO never treats the currently checked-out branch, `main`, or `master` as an inferred default. If a repository has no authoritative remote default (or has ambiguous remotes), spawn returns `DEFAULT_BRANCH_UNRESOLVED`. For a single repository or workspace root, set `defaultBranch` explicitly. For a workspace child, configure its primary remote with `checkout.defaultRemote` when needed and set its cached remote `HEAD` with `git remote set-head`. Repositories initialized by AO are the exception because AO records its branch choice when it creates them; older AO-created repositories are recognized and backfilled on first resolution.

## Worker and orchestrator roles

Workers implement tasks and own code changes. Orchestrators supervise a project and coordinate workers. Configure their harnesses independently:

```json
{
  "worker": {
    "agent": "codex",
    "agentConfig": { "model": "gpt-5.4", "permissions": "bypass-permissions" }
  },
  "orchestrator": {
    "agent": "claude-code",
    "agentConfig": { "model": "claude-opus-4" }
  }
}
```

The exact model names come from the installed provider. AO reuses the provider CLI and its existing authentication; it does not store provider tokens in project configuration.

## Session interface

Chat support depends on the harness and installed version; see the [agent capability catalog](/plugins/agents#chat-versus-terminal-ui).

Choose the default in **Settings → General**. An explicit new-task selection or `ao spawn --mode chat|tui` wins over the daemon default; otherwise the compatibility default is Terminal UI. An explicitly requested unsupported Chat mode fails; an inherited default may fall back to Terminal UI. `agentConfig.mode` is a provider execution mode, not this interface selector.

Supported sessions show **Switch to chat UI** or **Switch to terminal UI**. The available action depends on the harness, direction, and controller state. AO keeps the same session and worktree and replaces one controller at a time. When offered, **Finish work, then switch** waits for accepted work; **Stop now and switch** interrupts it. Some terminal transitions require **Terminate and then switch**. Read the dialog before continuing: unsent drafts, attachments, or queued turns may need to be sent again. Native provider history can be recovered where supported; terminal screen output is not converted into Chat messages.

## Setup and rules

Use `env`, `symlinks`, and `postCreate` for repeatable workspace setup. A failing `postCreate` command prevents the agent from starting, so keep setup deterministic.

Use `agentRules` or `agentRulesFile` for worker instructions and `orchestratorRules` for supervision-specific guidance. AO combines inline and file-based worker rules when both are present.

## Reviewer agents

Select reviewers independently in project settings; the [agent catalog](/plugins/agents) distinguishes reviewer support from worker and Chat support. Without an explicit reviewer, AO inherits Claude Code, Codex, OpenCode, Muse, or Kimchi from the worker; other workers fall back to Claude Code. Other reviewer harnesses must be selected explicitly.

Enable `autoReview` to copy automatic review into new worker sessions. Existing sessions have their own toggle. Eligible PR-head and idle checks still apply, and merge remains explicit.

```bash
ao review trigger <worker-session-id>
ao review ls <worker-session-id>
```

## Update from the CLI

Inspect the current configuration, then pass the complete replacement as a JSON object string:

```bash
ao project get <project-id> --json
ao project set-config <project-id> --config-json '{"worker":{"agent":"codex"}}'
```

The second command intentionally replaces the whole config with just that worker override. Preserve existing setup, rules, reviewers, and intake fields in real updates. Focused flags also build a replacement; they are not a patch. `--config-json` does not read a filename. Use `--help` for supported flags and `--clear` to reset.

## Choose The Workspace

AO selects isolation from the project kind: Git projects use worktrees; multi-repository workspaces materialize their repositories together; legacy Scratch projects use AO-managed plain directories. There is no `workspace: clone` or `runtime: process` setting.

For work without a project, use a standalone worker:

```bash
ao spawn --standalone --agent codex --name notes --prompt "Draft release notes"
```

Standalone requires an explicit agent and cannot combine with project, branch, issue, PR, or orchestrator options.

## Prepare Each Session

These fields belong in the stored JSON configuration, not a YAML file:

```json
{
  "symlinks": [".env", ".claude"],
  "postCreate": ["npm ci"]
}
```

Symlink paths are repository-relative and cannot escape the repository. A failing setup command prevents the agent from starting. Preserve the rest of the config when applying this fragment with `set-config`.

## Give Agents Project Rules

Use inline worker instructions, a repository-relative rules file, or both:

```json
{
  "agentRules": "Use conventional commits. Run the relevant tests before pushing.",
  "agentRulesFile": "AGENTS.md",
  "orchestratorRules": "Split large tasks into focused workers. Review results before merging."
}
```

Worker inline and file rules are combined. Orchestrator rules apply to the supervising role. For repeatable actions rather than standing instructions, manage project **Cues** in the desktop: an agent Cue sends a prompt, while a command Cue runs the exact command in a fresh local terminal.

## Split Orchestrator And Worker Roles

Each role can select a different harness and provider configuration:

```json
{
  "orchestrator": { "agent": "claude-code" },
  "worker": { "agent": "codex", "agentConfig": { "permissions": "bypass-permissions" } }
}
```

Model and effort choices depend on the selected provider. Choose permissions deliberately; bypass allows the provider's tools to act without normal approval prompts. The global Chat/Terminal UI default remains separate.

## Choose A Reviewer

Reviewers are an array of harness/config entries:

```json
{
  "reviewers": [{ "harness": "codex" }],
  "autoReview": true
}
```

Select reviewers independently in project settings; the [agent catalog](/plugins/agents) distinguishes reviewer support from worker and Chat support. Without an explicit reviewer, AO inherits Claude Code, Codex, OpenCode, Muse, or Kimchi from the worker; other workers fall back to Claude Code. Other reviewer harnesses must be selected explicitly.

Review instructions and provider permission modes are not OS isolation. Experimental reviewers may retain host authority or ask for native approval; check the selected harness before unattended use.

## Tracker And SCM

AO supports GitHub and GitLab repository observation and issue adapters. It resolves the repository from Git identity; there is no `tracker.plugin`, `scm.plugin`, `package`, or `path` plugin configuration. Linear is unsupported.

Use `canonicalRepoURL` when numeric PR claims should trust a particular upstream; it does not change where the session checks out or pushes. Issue spawning can select `--tracker-provider github|gitlab`. See [issue intake](/plugins/trackers) and [SCM authentication](/plugins/scm) for provider setup, including self-managed GitLab hosts.

Automatic intake requires both `AO_TRACKER_INTAKE=on` in the daemon environment and an enabled project `trackerIntake` with an assignee rule. It can spawn workers but does not comment on or transition issues.

## Tune Automation Per Project

Lifecycle reactions are built in; there is no project `reactions` override. Use `autoReview` for the default review toggle and `trackerIntake` for gated issue-driven spawning.

Create recurring tasks from **Automations** in the sidebar, and reusable instructions or commands from project **Cues**. These are stored resources, not additional ProjectConfig keys. See [Lifecycle automation](/configuration/lifecycle-automation) for schedule and delivery behavior.

## Session Recovery

Use the session's resume or restore action instead of legacy duplicate-session strategy fields. `ao session exit-agent <id>` stops only the controller; `ao session resume-agent <id>` starts it again. `ao session kill <id>` terminates the session, and `ao session restore <id>` restores it when recovery is supported.

Keep the harness installed and authenticated. Recovery can retain the session/worktree and supported provider conversation, but cannot recreate arbitrary terminal screen history. AO will not force-delete a dirty registered worktree. `orchestratorSessionStrategy` and `opencodeIssueSessionStrategy` are not current configuration.

## Local Reference

The [current configuration fields](#current-configuration-fields) table is the accepted ProjectConfig vocabulary. `agentConfig` and role overrides hold supported provider model, effort, mode, and permission choices; `reviewers` holds reviewer entries; `trackerIntake` holds the opt-in intake rule.

Identity such as project ID, path, and origin belongs to project registration. `sessionPrefix` is a typed config field. Unknown keys are rejected. Inspect the stored result with `ao project get <project-id> --json`; there is no parallel local YAML file or global registry file to maintain.

## Common Problems

**The project does not appear in the dashboard**  
Add it in the desktop or run `ao project add --path /absolute/path/to/repo`. `ao start` opens the app; it does not register the current repository. If the repo moved, remove and re-add or relink the project instead of editing `storageKey` manually.

**The agent starts without environment variables**  
Add `.env` or the relevant tool config directory to `symlinks`. AO does not copy secrets into worktrees by default.

**Setup fails before the agent starts**  
Check `postCreate`. A failing command stops the session before the agent launches.

**Two projects get confusing session names**  
Set `sessionPrefix` in project settings or typed config. Do not include path separators or traversal components.

**GitHub or GitLab calls fail**  
Make sure the corresponding CLI or token is authenticated for the plugin you use. AO does not store provider tokens in project config.
